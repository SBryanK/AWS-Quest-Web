# SA, PM and commitments

For Solutions Architect work, capture the customer problem, desired outcome, current system, functional and non-functional requirements, constraints and acceptance evidence. Separate confirmed requirements from assumptions. Record cost inputs with dates, protocols, regions, latency/availability requirements and security boundaries only when relevant. Compare options against constraints. Keep architecture decisions with their trade-offs and supporting source IDs. Build PoC tests with observable success criteria; do not call a proposed design validated.

For PM work, maintain scope, definition of done, owners, milestones, dependencies, risks and decision deadlines. Translate discussion into specific actions with acceptance criteria. Keep meeting notes separate from an evidence-linked action/decision index; “discussed” is not “approved.” Update the active plan from actual changes instead of copying full meeting transcripts into every session.

For commitments, track the actual commitment, due time/timezone, next physical action, expected effort, waiting-on person and status. Use Asia/Singapore only when appropriate to the user's context; preserve dates explicitly supplied in another zone. Creating a markdown row does not schedule anything. Use supported calendar/reminder tools only when requested/authorized and record success or failure accurately. Do not send messages merely because a task has an owner.

For a portfolio of projects, make a compact index with project path, outcome, next action, due date, blocker and updated date. Use the portfolio template only when several actual projects are in scope. Link into project-local context; avoid a giant cross-client memory document. A weekly review can identify the next three priorities and waiting items; scheduling that review is a separate automation request.

Useful optional specialized workflows: architecture decision/PoC review, meeting-to-actions, assignment execution, presentation storytelling, and weekly portfolio review. Add a standalone skill when the workflow repeats and cannot be handled by one concise prompt; do not turn every minor activity into a skill.
